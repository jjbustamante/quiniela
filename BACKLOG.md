- [ ] [P2][backend][frontend] test-mode deadline edits clobber the LIVE deadlines — the `/admin/test` deadline editor (`AdminTestService.setDeadlines`) writes the SAME `tournament.group_stage_deadline` / `knockout_deadline` columns the app reads in production. "Go live" (`setMode(false)`) and `clean()` do NOT restore them, so whatever you last dragged the deadlines to while simulating becomes the live deadline. Bit us 2026-06-07 (restored in prod via the V006 canonical UPDATE). **Deferred to post-kickoff per Juan.**
  - Immediate mitigation until fixed: don't drag deadlines during testing, or re-restore with `UPDATE tournament SET group_stage_deadline = TIMESTAMPTZ '2026-06-11 17:00 UTC', knockout_deadline = TIMESTAMPTZ '2026-06-28 17:00 UTC' WHERE id = 1;` (canonical V006 values: group Jun 11 17:00 UTC, knockout Jun 28 17:00 UTC).
  - Recommended fix (override model): treat the existing columns as canonical/live, edited only in `/admin/config`; add nullable `test_group_stage_deadline`/`test_knockout_deadline` companion columns the test panel edits instead. The single read chokepoint `LockClock.fetchTournamentDeadlines()` (every deadline read funnels through it — BracketService bracket view + bet-lock check + all others) returns `effective = (test_mode AND test_x IS NOT NULL) ? test_x : canonical_x`. Leak becomes impossible (no copy step; live always reads canonical), test power preserved (still drag test windows freely), `clean()` nulls the overrides. Small because LockClock is the only reader. Alternatives considered + rejected: restore-on-go-live (relies on a copy firing) and move-editor-to-config-only (kills the ability to test locked/open windows).

- [ ] [P3][backend][paul][enhancement] opponent-modeling avatars — the quiniela is a *statistics game* and every player's bets from prior rounds are public/visible to all. Today each oracle predicts matches in isolation (one model → a scoreline). Idea (Juan, 2026-06-28): give an avatar (or Paul) the **field** as context — live standings (`quiniela.points`), rounds remaining, the scoring rules (incl. `round.points_multiplier` ×2 knockouts), and every player's historical `bet` rows — so it picks bets **strategically to climb the ranking** (differentiate from the pack, take upsets when behind, protect a lead) rather than just predicting the most likely score. A meta-game / game-theory layer on top of the current per-match prediction, and a strong agent-design showcase.
  - Builds on the multi-oracle registry (PR #46: `paul_prediction.oracle`, per-oracle generate/synthesize/reveal, single-model avatars Otto/Chitara). A "strategic" oracle would be a new oracle *kind* (its prompt/agent consumes standings + bet history) rather than a plain single-model roster entry.
  - The data is already public and queryable (`bet` per round + `quiniela.points` + `round`) — this is a context-assembly + prompt/agent-design problem, not a data-access one.
  - Applies to **Paul first** (the flagship): Paul should play with all available info to maximize its own potential, not just predict each match in isolation. Design fork to decide: keep Paul an **honest oracle** (predicts the most likely outcome) vs. make it a **ranking-maximizer** (may take contrarian / higher-variance bets when behind, or play it safe to protect a lead). The latter is the more impressive agent but changes Paul's character — players treat his picks as the "expert" baseline, so a Paul that games the table for points could read as off-brand. Could be modeled per-oracle (e.g., Paul honest, avatars strategic) so both behaviors coexist and are comparable on the leaderboard.

### Tech debt / SOLID (from 2026-06-06 design review)
> Architectural findings from a SOLID review of the backend (`backend/src/main/java/io/quiniela/api`). Not bugs — code works today — but each is a "second reason to change has arrived" refactor. The `paul` package (`PaulOracle` + impls + `PaulOracleConfig`) is the reference pattern to imitate: narrow interface, multiple substitutable impls, conditional-bean wiring, stub-backed tests. Don't change it.

- [ ] [P3][backend][tech-debt] scoring rules duplicated across Java and the DB trigger (SRP/DRY) — the points algorithm lives in **both** `compare/CompareService.java::scoreMatchForBet` **and** the Postgres function (`db/migration/V005`→`V010`→`V016`→`V017`). **Correctness risk RESOLVED 2026-06-06 + guarded; full consolidation still open.**
  - ⚠️ The divergence was REAL, not hypothetical: the Java mirror was stale at the **V005 ladder (5/3/2)** while the DB had advanced to the **V010 additive model (outcome 3 + each-team-exact 2 + goal-diff 1, ×2 ko)**. The Duelos/H2H view was showing points that didn't match the actual leaderboard (e.g. an exact group pick showed 5 but really scores 7). Fixed `scoreMatchForBet` to the additive model + corrected `CompareH2HIT` expectations.
  - Guard added: `compare/ScoringDivergenceTest` exhaustively compares Java vs the live DB function across every 0–5 scoreline (group + knockout) in one round-trip — divergence now fails CI.
  - STILL OPEN (the real consolidation): two implementations of one rule remain. Options: (a) DB authoritative, Java calls a shared SQL scoring function / reads computed points; or (b) a Java `ScoringPolicy` used everywhere, trigger as a tested persistence optimization. NOTE: the knockout-multiplier work (Plan 1, merged `d37f82f`) already removed the hardcoded `* 2` — all 3 scoring paths now read `round.points_multiplier` as a shared column source, and `ScoringDivergenceTest` covers multipliers. The base additive rule is still duplicated (Java + PL/pgSQL); full consolidation per (a)/(b) remains.
  - KNOWN GAP in the Java mirror (documented in-code): it omits V016's knockout-regulation-draw refinement (predicted_winner_id vs advanced_team_id). The H2H view passes no winner ids so it matches the DB-called-with-NULLs today; this only matters once knockouts with penalty-draw picks are scored in the preview. Folds into the consolidation above.
  - UPDATE 2026-06-07: there is now a **third** scoring impl — `scoring/ScoreBreakdown.of()` (component breakdown for the player scorecard). Unlike the H2H mirror it DOES include the knockout-draw refinement, and `ScoreBreakdownDivergenceIT` pins its total to the live DB across 3,888 combos + draw cases. So the consolidation target is now: 1 DB function + 2 Java impls (CompareService total-only, ScoreBreakdown components) — a future `ScoringPolicy` could expose both `total()` and `breakdown()` and let CompareService/MatchesService/scorecard all use it.

- [ ] [P3][backend][tech-debt] `AdminTestService` is a God service (~450 LOC, ~5 reasons to change) (SRP) — one class owns authorization, real tournament domain logic (`groupStandings`, `seedKnockoutBracket`, `wireParents`, `advanceFromRound`, `fillThirdPlaceFromSfLosers`), match simulation (`randomGoals`, `simulateRound/All`), and test-mode/deadline admin (`setMode`, `setDeadlines`, `clean`).
  - Deeper smell: `groupStandings()` and `advanceFromRound()` are *real* tournament rules living inside a "test" service. If a public standings view is ever needed, you'll duplicate them or reach into test code (layering inversion).
  - Fix: extract a pure `StandingsCalculator` (matches → standings, no DB writes — trivially unit-testable) and `BracketSeeder`/`BracketAdvancer`; leave `AdminTestService` a thin orchestrator. Caveat: the *seeding matrix* may stay test-only (comment: "valid test bracket, NOT FIFA's official slotting") — but standings + advancement are general domain logic.

- [ ] [P3][backend][tech-debt] `tournamentId = 1L` / `poolId = 1L` hardcoded in ~18 sites across 12+ files (OCP) — `TOURNAMENT_ID`/`POOL_ID`/`DEFAULT_*`/`ACTIVE_*` constants repeated in CompareService, BracketService, PaulService, RankingService, MatchesService, FootballDataLoader, the payment + admin services, etc.
  - Defensible MVP/YAGNI shortcut today (single tournament, single pool) — **do not fix before kickoff**. Logged so the cost is visible: the day a 2nd tournament/pool is needed, this is an OCP wall — you must edit every site rather than extend.
  - Fix when the feature actually arrives: thread tournament/pool as parameters or a request-scoped context, not module constants.

- [ ] [P3][backend][tech-debt] inconsistent persistence wiring (style, not a true SOLID violation) — services split between Spring Data JPA repositories (BracketService, PaulService) and raw `JdbcTemplate` (CompareService, AdminTestService, AdminPaymentService, RankingService…), and AdminTestService mixes both. Both are valid abstractions (DIP intact); the inconsistency is the injection: some `new JdbcTemplate(ds)` in the constructor, AdminPaymentService injects `JdbcTemplate` directly. Pick one convention and document it (read-heavy projection queries are a fine reason to keep `JdbcTemplate` — just make it deliberate, not per-author drift).
